# v0.3.5 技术设计

更正：本版的资源回收竞争仅为当时推断，后续实机复测未解决故障。已确认的等待播放源配置错误和修复见 [v0.3.6](../v0.3.6/dev.md)。

## 上游与根因

严格模式的 Signal Tap 销毁后，Core Audio 可能尚未完成底层 IOProc 资源回收。旧实现的 `retry()` 同步执行 `stop()` 与 `start()`，新 Tap 偶发在 3 秒启动宽限内没有有效回调，`SignalHealth` 随后抛错；控制器按安全策略锁存故障并释放所有监听，因此自动归零确实停止。

## 控制器生命周期

`GuardController` 新增 `retryPending` 和 `.retrying`。显式重试先递增 generation、取消旧任务、停止服务并清除两类监听及恢复上下文，再安排一个 `now + 3s` 的单次任务。冷却期的 `refresh()` 直接返回，重复 `retry()` 也直接返回；截止回调还需同时匹配运行状态、pending 和 generation，保证最多重建一次。

睡眠会取消 pending 并显示 `.sleeping`，退出会同时取消任务和服务回调。唤醒不走人工冷却，沿用立即停止、启动、重新读取设备并给予完整空闲时间的路径。重建失败继续进入既有锁存故障，不启用忙重试，也不静默切换检测模式。

## 下游与资源

菜单展示新状态并在 pending 时禁用命令。偏好 JSON、HAL 写入、Signal Tap 配置、恢复提示、权限和安装数据均不迁移。冷却只占用一个已有调度器的单次任务，不创建轮询、线程、Tap 或辅助进程。
