# 全链路审计记录

v0.4.4 / build 20，2026-11-05。工作区起点为干净 main，原基线 123 项测试 / 610 次断言通过。本轮由当日实机诊断证据驱动（17:52:53 自动归零、18:16:01 恢复记录以“输出设备、路由、音量或静音状态已变化”作废、19 时新播放无弹窗；诊断历史 10-29 至 11-05 共 9 次同模式 recoveryInvalidated）。

## 实机证据与根因

恢复弹窗只存在于恢复分支：自动归零建立凭据后，设备/路由/音量/静音任何变化即作废凭据；作废后设备停在音量 0 时，活动监测需要音量大于 0、恢复监测需要凭据存在，两条路径同时不可用——守卫既不检测新播放（弹窗不可能出现）、也无法再次自动归零（空闲计费同样需要音量大于 0），状态栏显示“音量为 0，检测已休眠”。该死角只能靠用户手动调高音量解除，与用户认知（保护持续生效）不符。

## 范围与结果

| 链路 | 审查与处理 |
| --- | --- |
| 恢复失效 → 零音量守望 | 凭据作废且设备停在音量 0 时，下一个刷新周期自动重建隐式凭据，复用全部恢复链路 |
| 唤醒/重建/重启 → 守望 | 停在音量 0 的任何路径（睡眠唤醒、看门狗重建、写入故障恢复、应用重启）同样自动重新武装 |
| 用户显式选择 | “保持静音，不再提醒”与“立即归零”按设备抑制守望，音量离开 0 即解除；抑制不跨设备、不落盘、不被“重新核对”清除 |
| 建议音量 | 按设备 UID 记忆上次非零音量逐声道快照（路由变化不丢失）；未记录时建议 25% 并在弹窗与恢复写入中明确标注 |
| 守望失效 | 与自动凭据同一套复核：设备、路由、非零音量、静音、可控性、名单；守望从不写音量、从不自动恢复 |
| 守望启动失败 | 沿用“恢复检测启动失败”路径：作废凭据、保留归零成果、不伪报成功 |
| 状态 → 诊断 | 隐式武装记录 implicitWatch（同轮一条，防冲刷）；`--status` 新增 recoveryImplicit、zeroWatchSuppressed |
| UI → 文案 | 零音量子状态三分（守望/已确认保持静音/休眠）；设置页与开关确认说明守望规则与建议音量 |
| 弹窗 → 未记录原音量 | “未记录归零前音量，建议 X%”呈现，滑块、按钮、安全语义不变 |
| 文档 → 版本 → 安装 | 同步 0.4.4 / build 20 全套入口；安装与构建明确分离 |

## 自动化证据

当前核心回归 129 项 / 670 次断言通过，新增 6 项控制器回归（失效后重武装并完整弹窗恢复、保持静音抑制与解除、手动归零抑制与解除、未记录建议音量端到端、资格矩阵、守望自身失效）；既有断言中“设备/路由变化后无凭据、无监听”类预期按零音量守望新行为更新为“旧凭据失效 + 隐式守望在位”，恢复写入与旧 ID 拒绝语义全部保持。最终完整门禁和发行验证结果记录在[测试报告](TESTING.md)。

注入服务可验证状态机，不等同真实 HAL 路由抖动注入。真实虚拟声卡/显示器音频抢占后的自动重武装与弹窗需实机验收（A31）。

## 保留边界

- 键盘把音量调回 0 与凭据失效不可区分：会重新守望，持续播放可能多弹一次窗（可再次保持静音）——设计取舍，不是缺陷修复遗漏。
- 零音量守望使默认模式在音量 0 期间保留播放进程监听（严格模式保留信号 Tap）；长期 CPU/RSS 影响未定量测量。
- 守望凭据的建议音量依赖本会话记忆，重启后从头积累；未记录时 25% 为保守建议值。
- Core Audio 同步 API 可能阻塞；退避与看门狗不是硬超时；无 Developer ID/公证。
- 写入故障锁保持人工处理；自动路径从不调高音量、不恢复音量、不把守望期间算作空闲。
- 本地构建、安装、Git 提交、远端 CI 和公开 Release 是独立交付门禁，不相互推导。
